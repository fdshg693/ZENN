# YouCam API デモ（化粧ルーティンの共有・ドライラン）

YouCam API（Perfect Corp.）を使い、**サーバを持たないシンプルな静的サイト** として、
「化粧などのルーティンを API で実行してドライランし、その手順を他人と共有して自分の顔で試せる」ことを検証するデモ。

> API 仕様の調査メモは [docs/](./docs/) 配下にある。本デモの具体的な提供機能・利用 API は [PLAN.md](./PLAN.md) を参照。

## 前提

- サーバ等は持たない。**ユーザーが自分の API キーを入力** して利用する。
- 目的は「YouCam API の使いどころ・ユースケースを探る」こと。**他の技術的要素は重視しない**（描画品質・運用堅牢性は API 任せ／対象外）。

## このデモが目指すもの（スコープ内）

1. **ルーティンの実行（ドライラン）**
   - 化粧の各操作を「ブロック」として並べ、自分の顔写真に対して API で実行し、結果を確認できる。
   - 1ブロック=1化粧パーツ（または1機能）。複数ブロックをつなげて一連の手順として実行する。
2. **ルーティンの保存・共有（JSON）**
   - 組んだルーティンを **JSON としてエクスポート/インポート** できる。
   - 他人のルーティン JSON を取り込み、**ソース画像（自分の顔）だけ差し替えて** 同じ手順を試せる。
3. **化粧にフォーカスした最小 POC**
   - 特にインパクトのある化粧（メイク）系を中心に、肌診断・完成ルックを補助的に扱う。

## 範囲外（スコープ外）

- **動画・ライブ試着**（GRWM の本来の主役）。本デモは静止画ベース。
- **製品（買えるSKU）との連携**・EC カート・決済。
- **API キーの秘匿・本番運用**（CORS 回避、サーバ経由のプロキシ、課金管理など）。キーはユーザー入力でフロントに乗る前提。
- **描画品質そのものの改善**。API の出力をそのまま使う。
- **複雑な共有基盤**（アカウント、フィード、権限管理など）。共有は JSON の import/export に限定。
- **アプリの作り込み**（凝った UI/UX、フレームワーク選定等）。価値検証が射程で、プロダクト化はしない。

## 提供価値

### 目新しくない部分（代替品がある）

- **単体の試着・肌診断そのもの**: Banuba / ModiFace(L'Oréal) / DeepAR / GlamAR など競合 SDK/API でも可能。
- **EC のカート横での1製品 VTO**: 既存の VTO プラグインの主戦場。
- **描画リアリズム**: YouCam API の強みに乗るだけで、本デモ独自の価値ではない。

### 新たな価値（空白を埋める部分）

- **「手順（ルーティン）」としての合成・連結**: YouCam API は基本「1機能=1タスク」で、横断的な手順モデルを標準では持たない。複数操作を1つの再生可能な手順として扱うのは既存実装の空白。
- **設定の資産化＝共有**: 「その場で試して終わり」ではなく、ルーティンを JSON として保存し、**他人が自分の顔で再生** できる。試着体験を「配布可能なコンテンツ」に変える点が新しい。
- **1ショット体験 → プロセス体験** への転換: 「なぜこの順番・この色か」という手順の文脈を表現できる。

> 技術的な参入障壁は低い（描画は API 任せ、合成・共有は JSON 操作）。
> 価値は「難しい技術」ではなく **「誰もまとめていないワークフローを提示する」** 点にある。
> 詳細な価値分析は [docs/poc-value.md](./docs/poc-value.md)。

### 「API で1発でできること」との線引き（なぜアプリにするか）

makeup-vto は `effects` を**配列**で受け取るので、「skin_smooth + チーク + リップ」を**1リクエストで重ねて1枚に**できる（[docs/makeup-vto.md](./docs/makeup-vto.md) の複数パーツ適用）。
本デモの **一括方式（bundle）はこの API ネイティブ機能をなぞっているだけ**で、それ単体ではアプリの存在意義にならない。

正直な線引きとして:

| やりたいこと | このデモは要るか |
| --- | --- |
| メイク効果を自分の1枚に重ねたいだけ（単発・makeup のみ） | **不要**。[API Playground](https://yce.makeupar.com/api-console/) や `curl` で足りる |
| `effects` JSON を手書きせず GUI で組み、実行前に検証したい | あると楽（弱め） |
| **機能をまたいで**手順を組む（例: 肌診断 → メイク → 完成ルック） | **要る**。下記の理由で API 1発では不可 |
| メイク手順を**他人と共有し、相手が自分の顔で再生**したい | **要る**（機能F = 本命） |

技術的な要点は **「`effects` 配列が効くのは makeup-vto という1エンドポイントの中だけ」** という点:

- **一括（bundle）**: makeup の効果同士なら1配列＝1タスクに統合できる（API がエンドポイントレベルで対応）。
- **チェイン（chain）**: `skin-analysis`／`look-vto` など**別エンドポイントをまたぐ**手順は API 1発では組めない。前タスクの結果 url を次の `src_file_url` に渡す**連結はアプリ側のオーケストレーション**（[src/domain/routine.ts](./src/domain/routine.ts)）であり、ここは bundle で陳腐化しない。

つまりこのデモの存在意義は makeup 単発ではなく、**①機能をまたぐ連結（機能C chain + D/E）と ②ルーティンの保存・共有（機能F）** に乗って立ち上がる。
機能F（共有）まで作らないなら「Playground で十分」という問いはおおむね正当 ── **共有を作る前提があるか**が、このデモを正当化できるかの分かれ目になる。

## 想定ユースケース

- **クリエイター × ルーティン共有（最有力）**
  「あなたの GRWM を、フォロワーが自分の顔で再生できる」。自分の手順を配布物として共有する。
- **ビューティー教育/アドバイザー**
  手順を教材・処方箋として共有する。肌診断 → 提案 → 手順、の流れを商材化する。
- **D2C/インディーブランド**
  「このブランドで作る公式ルーティン」を配布し、UGC を誘発する。軽量導入の検証に。
- （補助）**自分用のルーティン管理**
  日々のメイク手順を保存し、写真でドライランして見比べる。
