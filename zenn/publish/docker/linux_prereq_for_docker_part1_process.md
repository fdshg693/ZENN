## カーネルとユーザー空間 — 「システムコール」とは何か

まず一番下の地面から。OS は大きく **2 つの層**に分かれています。

- **カーネル**: 特権を持つ中核。CPU・メモリ・デバイス・プロセスを直接管理する
- **ユーザー空間**: アプリ(あなたのプログラムや `nginx` など)が動く場所。ハードを直接は触れない

アプリが「新しいプロセスを作りたい」「ファイルを開きたい」「パケットを送りたい」といった**特権操作**をしたいとき、唯一の窓口が **システムコール(system call)** です。アプリはシステムコールを呼んでカーネルに依頼し、カーネルが代わりに実行します。「ユーザー空間とカーネルの間にある受付窓口」と捉えてください。

元記事に出てくる以下の 3 つは、すべてプロセスと隔離を操るシステムコールです(中身は前編が説明します)。

- `clone()` — 新しいプロセスを作る(`fork()` の親戚)
- `unshare()` — 自分自身を今の環境から切り離す
- `setns()` — 既存の隔離環境に参加する

### コンテナと仮想マシンの決定的な違い

ここが効いてきます。**仮想マシン(VM)は「別のカーネルごと」動かします**。ゲスト OS が丸ごと別に立ち上がる。一方 **コンテナは、ホストと同じ 1 つのカーネルを共有**し、「見え方」だけをプロセスごとに変えたものです。コンテナの中に別のカーネルは動いていません。

この一点が、前編の「コンテナはホストのカーネルの上で動くただ 1 つのプロセスにすぎない」という核心そのものです。

> 出典: [The Linux Kernel: Process Management (Boston University, PDF)](https://www.cs.bu.edu/fac/richwest/cs591_w1/notes/linux_process_mgt.PDF)

**→ 元記事のこの記述に効く**: 「ホストのカーネルの上で動くただ 1 つのプロセス」「`clone()` / `unshare()` / `setns()`」「仮想マシンのように別のカーネルが動いているわけではない」

## プロセスとは — PID・親子・プロセスツリー

**プロセスとは、実行中のプログラム 1 個**のことです。そして Linux では、新しいプロセスは必ず**既存のプロセスの「子」として**生まれます。最初の 1 個(PID 1)を根として、すべてのプロセスが 1 本の木(プロセスツリー)につながっています。

押さえる用語は次の通りです。

- **PID(Process ID)**: プロセスに付く一意の番号
- **PPID(Parent PID)**: そのプロセスを生んだ親の PID
- **fork → exec の 2 段モデル**: Linux はプロセスをこう作ります
  - `fork()` で、まず**自分自身の複製**を作る(親と同じ中身の子ができる)
  - 子の中で `exec()` を呼び、**中身を別のプログラムに置き換える**(PID はそのまま、コードだけ差し替わる)
- **デーモン(daemon)**: 常駐し続けるバックグラウンドプロセス。`dockerd` や `containerd` がこれ

> 「コピー機」のたとえが分かりやすいです。`fork()` は自分をコピーして 2 人になること。`exec()` はそのコピー用紙(同じ PID)の上の文書を別物に差し替えること。
> 出典: [Linux Process Management: Fork, Exec, and Beyond (abhik.ai)](https://www.abhik.ai/concepts/linux/process-management)

### プロセスツリーの読み方

`ps fxa` を打つと、インデント(字下げ)で親子関係が見えます。

```text
systemd(1)
 ├─ sshd(1001)
 │   └─ bash(1050)
 │       └─ vim(1100)
 └─ dockerd(900)
     └─ containerd(950)
```

左にあるほど祖先、字下げされたものがその子。**この読み方さえ分かれば**、前編の「`dockerd → containerd → containerd-shim → 実プロセス`」というツリーがそのまま読めます。

> 出典: [top(1) — man7.org](https://man7.org/linux/man-pages/man1/top.1.html)

**→ 元記事のこの記述に効く**: 「`ps fxa` で目で見える」「runc がツリーに現れない」(runc は起動後に終了済みなので、木に残らない)

## シグナル — プロセスへの「短い通知」

**シグナルとは、あるプロセスから別のプロセスへ送る、番号付きの短い通知**です。「止まって」「終了して」「子の状態が変わったよ」といったことを、プロセスの境界を越えて伝えます。電話というより、ドアをノックする回数で合図を送るイメージです。

よく出てくるシグナルはこれだけ覚えれば十分です。

| シグナル | 意味 | 既定の動作 | 捕捉できるか |
|----------|------|------------|--------------|
| **SIGTERM** | お願いベースの「終了して」 | 終了 | できる |
| **SIGKILL** | 問答無用の強制終了 | 終了 | **できない** |
| **SIGINT** | Ctrl-C による中断 | 終了 | できる |
| **SIGCHLD** | 子プロセスの状態が変わった通知 | 無視 | できる |

ポイントは 2 つです。

- **シグナルハンドラ**: プロセスは「このシグナルを受けたらこう処理する」という関数(ハンドラ)を登録できる。登録しなければ、そのシグナルの**「既定の動作」**(多くは終了)が実行される
- **SIGKILL と SIGSTOP だけは特別**で、ハンドラを登録できず、無視もできない。だから「絶対に殺したい」ときの最終手段になる

`docker stop` は、まず **SIGTERM**(お願い)を送り、一定時間(既定 10 秒)待っても終わらなければ **SIGKILL**(強制)を送ります。これが「`docker stop` が 10 秒待たされてから落ちる」挙動の骨格です。なぜ SIGTERM が効かないことがあるのか——その答えは次のセクションの「PID 1」にあります。

> 出典: [signal(7) — man7.org](https://man7.org/linux/man-pages/man7/signal.7.html)

**→ 元記事のこの記述に効く**: 「`docker stop` が送る `SIGTERM`」「タイムアウト後に `SIGKILL` で強制終了」

## PID 1・ゾンビ・init — 親が子を「看取る」仕組み

ここは前編の「PID 1 問題」に直結する、最も重要なセクションです。

### 子の死は、親が「看取って」初めて完了する

子プロセスが終了しても、それで終わりではありません。**親プロセスが `waitpid()` というシステムコールで子の終了情報を回収する(これを「reap = 刈り取る」と言う)まで、子はプロセス表に「死体」として残ります**。この回収されていない死体が **ゾンビプロセス**です。

- **reap(刈り取り)**: 親が死んだ子の終了ステータスを回収し、資源を解放すること
- **ゾンビ**: 死んだが reap されていないプロセス。1 個なら無害だが、溜まると PID(プロセス番号の在庫)を食い潰し、新しいプロセスを作れなくなる
- **孤児(orphan)**: 親のほうが先に死んだ子。行き場を失うので、**カーネルが PID 1 に里子として預け直す(再ペアレント)**

> ゾンビと孤児の関係: A→B→C という親子で B が C より先に死ぬと、C は孤児になり PID 1 へ再ペアレントされる。その後 C が死んだら、新しい親である PID 1 が reap する責任を負う。
> 出典: [My process became PID 1 and now signals behave strangely (HackerNoon)](https://medium.com/hackernoon/my-process-became-pid-1-and-now-signals-behave-strangely-b05c52cc551c)

### PID 1 はカーネルから特別扱いされる

プロセスツリーの根である PID 1 には、カーネルが 2 つの特別扱いをします。

1. **シグナルの黙殺**: カーネルは PID 1 に `SIGNAL_UNKILLABLE` というフラグを立て、**ハンドラを明示的に登録していないシグナル(SIGTERM 含む)を既定動作で配送しません**。つまり PID 1 のアプリがハンドラを書いていなければ、SIGTERM は何も起こさず黙殺される(ただしハンドラを登録すれば受け取れる)
2. **孤児の引き取り**: 前述の再ペアレント先として、孤児を reap する責任を負う

> Linux カーネルのソースでは、PID 1 に相当するプロセスに `SIGNAL_UNKILLABLE` フラグが立てられ、既定動作のシグナルがスキップされる。だから SIGTERM が「効かない」ように見える。
> 出典: [How is PID 1 made special and unkillable? (Unix & Linux Stack Exchange)](https://unix.stackexchange.com/questions/776687/how-is-pid-1-made-special-and-unkillable)

### init とは — PID 1 の責務に専念する小さなプロセス

普通の Linux では、PID 1 には `systemd` のような **init プロセス**が座り、「シグナルを子へ正しく転送する」「ゾンビを reap する」という地味な責務を引き受けています。

ところがコンテナでは、あなたのアプリ(`./my-app`)がいきなり PID 1 になります。アプリは init 用に作られていないので、SIGTERM を黙殺し(→ `docker stop` が遅い)、子を reap せず(→ ゾンビが溜まる)、という事故が起きます。

解決策が、前編に出てくる **`docker run --init`**。Docker 同梱の小さな init(**Tini**)を PID 1 に割り込ませ、シグナル転送とゾンビ刈り取りだけを肩代わりさせます。

> 出典: [Containers and Signal Handling: Why You Need to Care About PID 1 (Deni Bertović)](https://www.denibertovic.com/posts/containers-and-signal-handling-why-you-need-to-care-about-pid-1) / [Docker - init, zombies - why does it matter? (Stack Overflow)](https://stackoverflow.com/questions/49162358/docker-init-zombies-why-does-it-matter)

**→ 元記事のこの記述に効く**: 「PID 1 にはシグナルがデフォルトで配送されない」「死んだ子を reap する責務」「`docker run --init`(Tini)」——前編の PID 1 問題が、ここまでで完全に読み解けるはずです。

## ファイルシステムとマウント — `/`・マウントポイント・rootfs

Linux のファイルは、ドライブレター(`C:` など)で分かれていません。**すべてが `/`(ルート)を頂点とした 1 本のディレクトリツリー**にぶら下がります。

問題は「では別のディスクや別のファイル群を、どうやってこのツリーに加えるのか」です。その仕組みが **マウント(mount)** です。

- **マウント**: 別のファイルシステム(ディスク、イメージ、ネットワーク上の領域など)を、ツリーの**ある一点に接ぎ木する**こと
- **マウントポイント**: 接ぎ木する場所のディレクトリ。例えば USB メモリを `/mnt/usb` にマウントすれば、`/mnt/usb` 以下にその中身が見える
- **rootfs(ルートファイルシステム)**: `/` に見えるファイル一式。コンテナにとっての rootfs は「そのコンテナから見えるルートの中身」

つまりコンテナの `/` は、ホストの `/` とは別物です。Docker はイメージの中身を rootfs としてマウントし、それをコンテナの `/` に見せています。

補足で 2 つ知っておくと前編が読みやすくなります。

- **読み取り専用 vs 書き込み可能**: イメージの層は読み取り専用、コンテナの変更分は書き込み可能な層、という区別がある
- **`/proc` と `/sys`**: 実在するファイルではなく、**カーネルの内部情報をファイルのように見せる特別な領域**。前編が覗く `/sys/fs/cgroup`(資源制御の状態)もこれ

> 出典: [mount(8) — man7.org](https://man7.org/linux/man-pages/man8/mount.8.html) / [path_resolution(7) — man7.org](https://man7.org/linux/man-pages/man7/path_resolution.7.html)

**→ 元記事のこの記述に効く**: 「rootfs」「OverlayFS の merged がコンテナの `/`」「mount namespace(マウントの見え方を隔離)」「`/sys/fs/cgroup` を読む」

## copy-on-write — 「コピーは書き込むまで遅延する」

**copy-on-write(CoW、書き込み時コピー)** は、効率化の定番テクニックです。考え方は一文で言えます。

> 同じ中身を複数で共有している間はコピーしない。誰かが**書き換えようとした瞬間に**、その分だけ初めて複製する。

これがなぜ嬉しいか。読むだけなら共有のままで済むので、**コピーのコスト(時間とメモリ/ディスク)を、本当に変更が必要になるまで先送り**できます。

CoW は Linux のあちこちで使われていて、前編に出てくる 2 か所も同じ発想です。

- **fork のメモリ**: `fork()` で子を作るとき、親のメモリを丸ごと複製はしない。親子で同じメモリページを共有し、どちらかが書き込んだページだけを複製する
- **OverlayFS の `copy_up`**: コンテナが読み取り専用イメージ層のファイルを**変更しようとしたとき**だけ、そのファイルを書き込み可能な層へコピーしてから書く

ここで前編の落とし穴が理解できます。OverlayFS の `copy_up` は**ファイル単位**なので、巨大なファイルの 1 バイトを書き換えるだけでも**ファイル全体がコピー**される。「大きなファイルへの初回書き込みが妙に遅い」のはこのためです。

> 出典: [Linux Process Management: Fork, Exec, and Beyond (abhik.ai)](https://www.abhik.ai/concepts/linux/process-management)

**→ 元記事のこの記述に効く**: 「既存ファイルへの初回書き込みで `copy_up` が起きる」「`copy_up` はファイル単位」

## ユーザーと権限 — UID/GID・root・特権

Linux は「**誰が**その操作をしようとしているか」で許可・不許可を決めます。その「誰が」を表すのが番号です。

- **UID(User ID)**: ユーザーを表す番号
- **GID(Group ID)**: グループを表す番号
- **root(UID 0)**: 特別なユーザー。ほぼすべての操作が許される**特権ユーザー**
- **一般ユーザー**: 自分の持ち物しか触れない非特権ユーザー
- **`sudo`**: 一時的に root 権限で操作を実行するコマンド

### なぜこれがコンテナのセキュリティに効くのか

ここが前編の User namespace の話に直結します。**権限は UID の番号で判定される**ので、もし「コンテナの中の root(UID 0)」と「ホストの root(UID 0)」が**同じ番号のまま**なら、コンテナ内 root は実質ホストの全権を持つことになります。

前編が言う「Docker はデフォルトで User namespace を有効にしない」とは、つまり**既定ではコンテナ内 root = ホスト root**、ということです。User namespace を使うと、コンテナ内の UID 0 をホストの非特権 UID(例: 100000)にマップでき、「コンテナ内 root ≠ ホスト root」にできます。

> 補足: root の全権は、実際には **capabilities** という単位で細分化されています(「ネットワーク設定だけ許す」など)。前編で深入りはしませんが、「root 権限はオールオアナッシングではなく分割できる」とだけ知っておくと、コンテナの権限設計の話が読みやすくなります。
> 出典: [capabilities(7) — man7.org](https://man7.org/linux/man-pages/man7/capabilities.7.html) / [credentials(7) — man7.org](https://man7.org/linux/man-pages/man7/credentials.7.html)

**→ 元記事のこの記述に効く**: 「コンテナ内 root(UID 0)をホスト側の非特権 UID にマップできる」「Docker はデフォルトでは User namespace を有効にしない」

## 調査の道具箱 — 元記事のコマンドを読む早見表

前編には調査コマンドがいくつも出てきますが、どれもここまでの概念に 1 対 1 で対応しています。「何を見るための道具か」を対応づけておけば、コマンド列に怯む必要はありません。

| コマンド | 何を見る | 対応概念 |
|----------|----------|----------|
| `ps` / `ps fxa` | プロセス一覧 / 親子ツリー | プロセス・PID(本稿§プロセス) |
| `ss -tlnp` | listen 中のポートとプロセス | ポート(→ ネットワーク編) |
| `stat -fc %T /sys/fs/cgroup/` | そのファイルシステムの種別 | マウント・FS 種別(本稿§FS) |
| `cat /sys/fs/cgroup/.../memory.events` | カーネルが見せる資源制御の状態 | `/sys` は特別な FS(本稿§FS) |
| `/var/lib/docker/overlay2/<id>/` | Docker が使う実体のパス | rootfs・層(本稿§FS, §CoW) |
| `$(...)` | コマンドの出力をその場に埋め込む | — |

最後の `$(...)` だけ補足します。前編の `PID=$(docker inspect --format '{{.State.Pid}}' <id>)` は、「`docker inspect ...` を実行し、その出力を変数 `PID` に入れる」という意味です。`$(コマンド)` は**コマンドの実行結果を文字列として埋め込む**シェルの記法(コマンド置換)です。

> 出典: [ss(8) — man7.org](https://man7.org/linux/man-pages/man8/ss.8.html)

**→ 元記事のこの記述に効く**: 前編のデバッグ実践に出てくるコマンド列全般。「これは何を確認しているコマンドか」で読めるようになります。

## まとめと後編(ネットワーク編)への橋渡し
