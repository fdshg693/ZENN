> 「クラウド閉域を理解するためのネットワーク基礎」シリーズの記事 1 です。
> 記事 0(OSI/TCP-IP モデル)で層の地図を用意しました。この記事はその中心、**L3(ネットワーク層)** に降りて、すべての出発点である IP アドレスと、それを区画に切る CIDR / サブネットを掘ります。

## この記事が解く誤解

閉域でいちばん最初につまずくのが、これです。

> **「プライベート IP を割り当てたのだから、もう閉じているはず」**

結論から言うと、これは誤解です。プライベートサブネットに置いた VM でも、経路と DNS が公開側を向いていれば普通にインターネットへ出ます。なぜそうなるのかを理解するには、「IP アドレスとは何か」「プライベートとは何が違うのか」「サブネットに切るとは何をしているのか」を原理から押さえる必要があります。

## IP アドレスとは何か

IPv4 アドレスは **32 ビット**の数値です。人が読みやすいように 8 ビットずつ 4 つに区切り、それぞれを 10 進数で書きます。

```
   192   .   168   .    0    .    10
11000000 . 10101000 . 00000000 . 00001010   ← 実体は 32 ビット
```

この 32 ビットは、概念的に **ネットワーク部**と **ホスト部**の 2 つに分かれます。

- **ネットワーク部**: 「どのネットワーク(区画)に属するか」を表す前半
- **ホスト部**: 「その区画の中の何番目か」を表す後半

郵便の住所に例えるなら、ネットワーク部が「○○市○○町」、ホスト部が「△番地」です。同じ町(ネットワーク)の中なら直接やり取りでき、別の町へ届けるにはルータ(郵便局)が要る——この区別が、次の記事 2 のルーティングにつながります。

では「どこまでがネットワーク部か」を、どうやって決めるのか。それが **サブネットマスク / CIDR** です。

## CIDR とサブネットマスク

**CIDR 表記**は、IP アドレスの後ろに `/24` のようにスラッシュと数字を付けます。この数字が **「ネットワーク部が先頭から何ビットか」** を表します。

```
192.168.0.0/24
            ↑ 先頭 24 ビットがネットワーク部、残り 8 ビットがホスト部
```

`/24` なら、ホスト部は 32 − 24 = 8 ビット。8 ビットで表せるのは 2^8 = **256 個**のアドレスです(192.168.0.0 〜 192.168.0.255)。

プレフィックス長と区画サイズの対応を覚えておくと、設計で迷いません。

| CIDR | ホスト部ビット | 総アドレス数 | イメージ |
|------|-------------|------------|---------|
| `/8` | 24 | 16,777,216 | 非常に巨大 |
| `/16` | 16 | 65,536 | 大きな区画 |
| `/24` | 8 | 256 | 小さな区画(よく使う単位) |
| `/28` | 4 | 16 | ごく小さい |

ここで **最重要の感覚**を 1 つ。**`/n` の数字が大きいほど、区画は小さくなります。** `/24` は `/16` よりずっと狭い。この「数字が大きい=より具体的で狭い」という性質が、記事 2 で出てくる **最長プレフィックス一致**(より具体的な経路が勝つ)の核心になります。ここで腹に落としておいてください。

### ネットワークアドレスとブロードキャストアドレス

ひとつの区画では、両端の 2 アドレスが特別な意味を持ちます。

- **ネットワークアドレス**(ホスト部がすべて 0): 区画そのものを指す名前。例 `192.168.0.0/24` の `192.168.0.0`。
- **ブロードキャストアドレス**(ホスト部がすべて 1): その区画全員への同報。例 `192.168.0.255`。

このため `/24`(256 アドレス)で実際にホストへ割り当てられるのは原則 254 個です。

:::message
クラウドではさらに数アドレスが予約されます。例えば AWS は各サブネットの先頭 4 つと末尾 1 つ、計 5 アドレスを予約します。Azure も同様に各サブネットの先頭側を予約します。「/28 で 16 個あるはずなのに 11 個しか使えない」のはこのためで、過小な CIDR を切ると IP 枯渇の原因になります。
:::

## パブリック IP とプライベート IP

ここがこの記事の山場です。IP アドレスには **グローバルに一意でなければならないもの(パブリック)** と、**組織内で自由に使ってよいもの(プライベート)** があります。

**プライベートアドレス**として予約されているのは、**RFC 1918** で定義された次の 3 レンジです([pfSense Documentation](https://docs.netgate.com/pfsense/en/latest/network/addresses.html))。

| レンジ(CIDR) | 範囲 | よくある用途 |
|--------------|------|------------|
| `10.0.0.0/8` | 10.0.0.0 〜 10.255.255.255 | 大規模な社内・VPC |
| `172.16.0.0/12` | 172.16.0.0 〜 172.31.255.255 | 中規模 |
| `192.168.0.0/16` | 192.168.0.0 〜 192.168.255.255 | 家庭・小規模 |

これらは **インターネット上では使われない(ルーティングされない)** と決められているため、誰でも自分のネットワーク内で自由に使えます。あなたの自宅の `192.168.0.10` と、隣家の `192.168.0.10` は衝突しません。両方ともインターネットには直接出ていかないからです。

ほかにも覚えておくと役立つ予約レンジがあります。

- **`169.254.0.0/16`(リンクローカル)**: DHCP に失敗したときなどに自動付与される。ルータはこのレンジを外へ転送しない([pfSense](https://docs.netgate.com/pfsense/en/latest/network/addresses.html))。クラウドのメタデータエンドポイント `169.254.169.254` もこのレンジ。
- **`100.64.0.0/10`(CGN, キャリアグレード NAT)**: ISP やクラウドが内部で使う([Azure: traffic routing](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-networks-udr-overview))。

### ここが誤解の正体

プライベートアドレスは「インターネットでルーティングされない」だけで、**それ自体がファイアウォールでも閉域装置でもありません。**

プライベート IP を持つ VM がインターネット上のサーバーと通信できるのは、出口に **NAT**(記事 2)があってプライベート IP をパブリック IP に変換してくれるからです。逆に言えば、

- NAT 経由の経路があれば、プライベート IP のままでも外に出られる
- 公開サービスの DNS 名が公開 IP に解決されれば(記事 4)、そこへもアクセスできる

つまり「プライベート IP を割り当てた」だけでは何も閉じていません。**閉じるのは、この後の記事で扱う「経路(ルーティング)」「通行制御(ファイアウォール)」「名前解決(DNS)」の層**なのです。これが閉域記事の言う「プライベート IP 空間があるだけでは閉域ではない」の正体です。

## サブネットに切る意味

ひとつの大きな区画(例 `10.0.0.0/16`、65,536 アドレス)を、より小さなサブネット(例 `10.0.1.0/24` や `10.0.2.0/24`)に分割することを **サブネッティング**と呼びます。

なぜ分けるのか。**サブネットが、ルーティングやアクセス制御の単位になる**からです。

- 「このサブネットは外に出られる(パブリックサブネット)」「こちらは出られない(プライベートサブネット)」をルートテーブルで切り替える(記事 2)
- 「このサブネットへの通信は弾く」をネットワーク ACL で切る(記事 3)
- 「このサブネットは AZ-a、こちらは AZ-c」と可用性ゾーンに割り当てる

区画を小さく切っておくことで、「どこに何を置き、どこを閉じるか」を細かく設計できるようになります。

## クラウドへの対応づけ

ここまでの汎用概念は、クラウドの部品にきれいに対応します。

| 汎用概念 | AWS | Azure |
|---------|-----|-------|
| 自分専用の IP 空間 | VPC(CIDR を指定) | VNet(アドレス空間を指定) |
| その中の区画 | サブネット(AZ に紐づく) | サブネット |
| 区画内の自動到達経路 | ルートテーブルの **local ルート** | システムルートの **Virtual network** |

AWS で VPC を作るときに `10.0.0.0/16` のような CIDR を指定するのは、まさに「自分のプライベート IP 空間を、この区画として確保する」という宣言です。そして VPC のルートテーブルには、**VPC の CIDR 宛の "local" ルートが既定で入っており**、これが「同じ VPC 内なら互いに到達できる」を担保しています([AWS: Subnet route tables](https://docs.aws.amazon.com/vpc/latest/userguide/subnet-route-tables.html))。Azure も VNet のアドレス空間に対して「Virtual network」というシステムルートが同じ役割を果たします([Azure: traffic routing](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-networks-udr-overview))。

閉域記事の **「①境界 = プライベートな IP 空間と区画」** が、まさにこの VPC/VNet + サブネットの設計です。

## 落とし穴

- **CIDR レンジの重複**: VPC ピアリングやオンプレ接続をすると、両側で同じ `10.0.0.0/16` を使っていた、という衝突が起きる。後から変更は困難なので、設計時に「将来つなぐ相手」と重ならないレンジを選ぶ。
- **過小なサブネット**: `/28` は実質 11 個程度しか使えない(前述の予約分)。スケールするワークロードを狭い CIDR に置くと IP 枯渇する。
- **「プライベート IP = 閉域」の誤解**: 本記事の核心。プライベート IP は出発点にすぎず、閉じる作業は経路・通行制御・DNS の各層で別途行う。

## まとめ

- IP アドレスは 32 ビット。**ネットワーク部 + ホスト部**に分かれ、その境界を **CIDR(`/n`)** が決める。
- **`/n` が大きいほど区画は小さい**。この感覚が記事 2 の最長一致につながる。
- **プライベート IP(RFC 1918 の 3 レンジ)** はインターネットでルーティングされないだけで、閉域装置ではない。外に出られるかは経路・NAT 次第。
- **サブネット**は、ルーティングやアクセス制御をかける単位。VPC/VNet + サブネットが閉域記事の「①境界」。

区画はできました。では、**ある区画から別の区画(やインターネット)へ、パケットはどうやって運ばれるのか**。そして「プライベート IP のまま外に出る」を可能にしている NAT とは何か。次の記事 2 で、ルーティングと NAT を掘ります。
